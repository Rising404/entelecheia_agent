# Entelecheia L1：链路失败归因与调整建议 / Failure attribution

整理日期：2026-09-11。汇总 Opus 5 错题归因与 Astra 链路审计。
原始选集为 125 题；本文排除需要联网的 `docbench:26:4`、`docbench:37:4`，按共同 **123 题**及其中 8 题补跑统计成绩和按题比例。逐题数据见[汇总数据](../../showcase_125.summary.json)。

## 1. 主要发现

双方都发现了真实的验证误拦、视觉/文本使用不当、精确统计困难及交付后处理缺口，
但它们对某些根因和推进顺序有不同判断，不能直接拼成一个确定结论。

- **Opus 5 的重点**：语义门会拦住正确核心答案；视觉使用频繁且观察不稳定；缺少可靠的文档统计能力。
- **Astra 的重点**：先修确定性的引用/回读接口、按页读取执行范围和视觉生成完整性，
  再比较 Gate 策略；不能把所有低分解释为模型能力或检索算法问题。
- **合并判断**：采用后者作为建议实施顺序，同时保留 Opus 5 指出的误拦与统计问题。

“存档确证”表示原审计给出轨迹、持久状态或代码的直接支持；“评审判断”表示对答案/候选的
模型辅助解释；“强推断”表示还缺原始响应或对照；“待验证”表示需要新的实验。
以下分析依据当时的审计记录和派生统计。

实际链路为：
文件接收/准备 → 精读/检索/视觉 → 模型决定与公开笔记 → 引用和语义检查 → 正式交付
→ 历史索引、摘要与窗口释放。每个箭头都可能出现“前一步成功，下一步未完成”。

## 2. 29 题遭拒，究竟是哪一层

### 2.1 不同统计单位

| 层次 | 首跑观察 | 正确解释 |
| --- | --- | --- |
| 模型输出 schema/admission 修复 | 9 题、19 次拒绝事件 | 同一逻辑模型调用内修正输出，不是 19 道终局失败 |
| 候选机械检查拒绝 | 23 题、25 次事件 | 全部集中在引用的 chunk 身份不匹配 |
| 候选语义检查拒绝 | 10 题、32 次事件 | 后续 Attempt 重新组织/提交候选 |
| 机械或语义拒绝并集 | 29 题、57 次事件 | 两组重叠 4 题，不是 33 题，更不是 29 道最终失败 |
| 最终执行失败 | 8/123（6.50%） | 4 次验证失败、3 次终局模型传输失败、1 次工具完成未确认 |
| 保存实质答复后进程异常退出 | 另 6/123（4.88%） | 与前述 8 题不重叠，不能直接按无答案计分 |

机械/语义重叠的 4 题为 2:0、30:2、40:0、118:1。
Opus 5 所述的 10 题对应**语义拒绝**，不含全部机械拒绝。

按共同 123 题复算，共 172 次最终候选提交，其中 25 次先被机械检查拒绝，
147 次进入语义 reviewer。147 对应语义审核响应数。
共同 123 题首跑有 840 个持久 Attempt 行、838 个保存的决定/笔记；
857 个成功返回的 L1 attempt 模型响应，加 147 个 reviewer 响应、122 个入口分类响应，
共 1,126 个带 usage 的主模型响应。重试使模型响应数与 Attempt 数不同。

Opus 5 对 183:0 写“40 次 L1 attempt 调用”混入了响应后的拒绝诊断：
存档为 24 个 Attempt、32 个成功响应加 8 个 admission 拒绝事件，合为 40 条相关事件，
不是 40 次模型调用。40:0 同理为 24 个 Attempt、25 个响应和 1 个拒绝诊断。
这些数字不能再次相加计算 token。

### 2.2 Opus 5 对十道语义拒绝题的解释

下表列出 Opus 5 对十道题核心候选和最终结果的判断。
“审核响应数”不是拒绝次数；部分题还经历机械拒绝。

| Case ID | 语义审核响应数 | Opus 5 对核心候选和最终结果的判断 |
| --- | ---: | --- |
| 183:0 | 9 | 多次正确核心候选被旧视觉观察否定，最终未实质交付 |
| 40:0 | 8 | 核心候选正确，跨页伪矛盾与机械引用问题叠加，最终未实质交付 |
| 30:2 | 6 | 不确定性措辞反复被要求修改，最后答对 |
| 148:2 | 3 | 候选依赖估算而非全文统计，首跑未实质交付 |
| 2:0 | 2 | 最终答对；不能只写机械引用原因，该题也有语义拒绝 |
| 73:4 | 2 | 页数证据解释与物理/印刷口径纠缠，Opus 5 最终给核心分 |
| 117:0 | 2 | 缺少可靠频次统计，首跑未实质交付 |
| 118:1 | 2 | Opus 5 认为候选得到真实纠正后答对 |
| 119:2 | 2 | 读取 partial 与“完整阅读”措辞冲突，最终答对 |
| 160:2 | 2 | 首个无依据精确值被拒，但后续无可靠统计的估计仍获交付且答错 |

Opus 5 将这组概括为纠正 1 题、损失 2 题，其余增加成本或未挽回错误，并给出“净 −1”。
按共同 123 题口径，最终实质交付的 15 个首跑错误都通过语义门，14 个一次通过。
这是该作者对既有候选的事后判断，**不是 always/off 配对消融**；
不能由此推出关门必然提高 1 分、Gate 普遍无益或一定不会引入其他错误。

十题共消耗 input 3,312,171 token、177 个 L1 响应、逐题耗时累计约 5,134.405 秒，
共同 123 题的首跑对应总量为 14,137,803 input token、857 个 L1 响应、31,426.478 秒，
上述十题分别占 23.43%、20.65%、16.34%。这是十题的**总成本**，
不是全部由语义门额外产生的边际成本。

原轨迹中 reviewer 原始输出正文未完整公开，Opus 5 的具体拒绝理由部分来自下一轮笔记转述。
因此可确认拒绝事件与相关证据组合，不能把模型转述当作 reviewer 的逐字原始日志。

## 3. 引用与历史回读：可以定位的接口问题

### 3.1 正确存在的 ID 被放进错误字段

Astra 审计中 23 题、25 次机械拒绝均为 `chunk_not_in_referenced_result`。
20 题涉及视觉 observation 身份，3 题涉及文本 element 身份。
29 个细粒度 ID 真实存在于所引结果中，但它们不是 `chunk_id`；
这不是 29 次凭空伪造证据，也不是需要放弃来源校验的理由。

现行职责链要求模型用 `tool_result_id` 加可选 `chunk_id` 引证。
schema 接受字符串，机械检查才发现其不是结果中的 chunk。
最后的错误反馈缺少引用下标、错误值和允许的改法，模型只好重写整份候选。
22/23 题后来恢复；40:0 还叠加语义审查问题。

建议在已有协议说明中明确：仅在原结果真实含 chunk_id 时填写，其他类型可引用整个结果；
Host 反馈指出 `/references/i/chunk_id` 和经过授权校验的来源信息。

### 3.2 历史保存了，但回读参数经常错

首跑 `read_tool_result` 73 次，26 次成功，47 次 `history_path_unavailable`，集中在 8 题。
其中 45 次使用了工具描述示例中的同一路径 `/result/text`；实际文本/视觉结果并无通用 text 字段。
另两次是页数组路径和单复数路径错误。失败只报 code，不提示合法键。

这证明接口指引有问题，不证明历史数据全部丢失：例如 40:0 的 17 次历史回读全部成功。
另有 10 次 admission 拒绝涉及把“历史回读的外层回执”当作原始来源；
当前上下文恰好只有回执时，通用的“引用当前结果”反馈还会误导重试。

建议默认读取根对象，按真实结构选择子路径；授权通过后，非法路径反馈其父对象合法键，
并用 `source.tool_result_id` 说明原始来源，区分未知 ID、失败结果和回读回执。

### 3.3 文件和版本身份也有混淆

120:4、129:0、170:3 曾将 document 身份传入 `retrieve_files.file_ids`，
外层工具执行成功但结果为文件不可访问、零证据；151:3 又将 file-version 身份传给
document-version 参数。它们属于参数语义/反馈问题，不能自动归为用户撤销授权或 RAG 没有运行。

## 4. 文档读取、覆盖与统计

### 4.1 指定一页不代表只解析一页

Astra 对 61:6 的记录是：207 页 PDF，`read_pdf_text` 14 次超时，
13 次只请求一页，另一次请求两页；累计约 422.381 秒。
冻结工具先调用 native reader 读取整篇，再筛页和限制返回元素。
因此页参数和字符预算限制的是返回结果，不是底层解析工作量。

延长整个 Turn 只能容纳更多相同超时；结果超时被拒收也不证明底层解析立即停止。
建议 reader 真正按请求页提取，或复用同一文件版本的已保存 source elements，
同时保留页码和错误信息。

### 4.2 小窗口、游标和 partial 被误读

冻结 `read_pdf_text` 默认返回 12 个、最多 16 个文本元素，字符上限 8,000。
Opus 5 发现单页密集版面有 158 个元素，第一页窗口并不等于完整页面。
Astra 对 140:0 的审计更具体：相关页已入库，但请求多个页面只返回最前面的有限元素，
模型未续读却跳去查看后续页；关键句没有进入被抽查的 7 次模型请求。
这是“已准备但未读到”，不是已证明的索引损坏。

148:2 **补跑**中 20 次沿用同一 element_offset；后续 cursor 已返回而未被采用。
不能说 cursor 在整条链路都丢失，更不能把这段补跑轨迹当成首跑机制。
模型还把字符量、词量和读取覆盖混为一谈，工具返回了内容却在最终回复中否认可读。

不同字段的 partial 至少涉及：
本次读取窗口没完、候选打包截断、解析覆盖缺口、未解释视觉区域，以及其他来源被排除。
“返回窗口 partial”不意味着“PDF 后续页不存在”；“页面有视觉元素”也不意味着文字层无用。
建议在工具结果中讲清 cursor、实际返回页/元素、来源覆盖与下一步读取方式。

### 4.3 151:3：两份报告的根因不一致

| 来源 | 观察或解释 | 合并处理 |
| --- | --- | --- |
| Opus 5 | 字面搜索量少于单独 PDF 文字抽取，判断解析不完整 | 保留为原作者推断，不直接当成已证实漏页 |
| Astra 库内审计 | 209/209 页、6,632 个 source elements 已保存；严格字面与空格/连字符规范化口径不同 | 比“搜索少”更能限定覆盖判断，但页齐不保证每个字符都正确 |
| Astra 工具审计 | 后续搜索用了错误版本 ID，得到 version unavailable | 这是独立可定位的参数错误，不能归为解析器故障 |

字面计数少或前几页 chunk 列表不足以证明整篇未入库。
规范化、换行连字符、词边界和抽取器不同，可能产生不同统计，需要统一定义后再比较。

### 4.4 缺的是可靠统计组合，不是所有基础能力都没有

Opus 5 的计数/页数/词数组共 6 题：69:4、111:1、117:0、148:2、151:3、160:2，
首跑核心分均 0，其中两题补跑仍 0。方向值得优先研究，但“没有计数工具”表述过宽：
现有文件权威已提供物理页数，`search_file_text` 也能统计 source elements 的字面命中。
短板是全文词数、缩写频次等可解释聚合、完整来源选择，以及模型对现有数字的正确使用。

统计应在去重的原文层进行，不对有重叠的 chunk 求和，也不对视觉摘要计数。
必须明确物理/印刷页、大小写、词边界、连字符、页眉页脚、OCR 重复和分词方法。
Opus 5 在一份文档上空白分词与参考吻合，不能推出所有 DocBench 词数题都采用该方法；
其他文档的抽取结果已经存在不同口径。

改进方向是扩展文档工具的确定性统计能力，让模型取得可核查的全文统计结果。

## 5. 视觉：使用策略、完成状态、解释质量分开看

### 5.1 工具分布与观察性关联

共同 123 题首跑的 784 次工具调用中，`analyze_pdf_page` 175 次，`read_pdf_text` 152 次，
`prepare_files` 123 次，`retrieve_files` 116 次，`read_tool_result` 73 次，
`check_files_state` 69 次，`read_file_chunks` 42 次，`search_file_text` 15 次，
`inspect_file_chunks` 11 次，`list_tool_results` 7 次，`find_files` 1 次。
按 Opus 5 选定的文件/结果管理工具集合：`prepare_files` 123 + `check_files_state` 69 +
`read_tool_result` 73 + `list_tool_results` 7 + `inspect_file_chunks` 11 = 283 次，
占全部 784 次的 36.10%。这是 Opus 5 的人工职责分组，不是唯一分类，也不意味着这些调用都是无效开销。

按共同 123 题统计，54 题曾收到需要视觉的诊断，46 题随后调用视觉；共有 64 题使用过视觉工具。
native reader 遇到图片/未解释矢量元素就可能标视觉缺口，表格线也能触发，
与文字层能否回答当前问题不是同一判断。

| 题型 | 用视觉题数 | Opus 5 判对 | 未用视觉题数 | Opus 5 判对 |
| --- | ---: | ---: | ---: | ---: |
| Text | 13 | 10 | 37 | 34 |
| Multimodal | 15 | 12 | 10 | 8 |
| Metadata | 19 | 12 | 6 | 4 |
| Unanswerable | 17 | 14 | 6 | 6 |
| 合计 | 64 | 48 | 59 | 52 |

使用视觉组为 48/64（75.00%），未用组为 52/59（88.14%），受题型、难度和“文本未解决才转视觉”的自选择混杂。
时间先后不等于诊断导致了调用，更不能据此断言视觉降低正确率。
文本优先策略的实际收益仍需实验验证。

### 5.2 32:1：19 次工具成功不等于 19 次新视觉推理

Astra 记录同一图表请求的 19 次工具结果文本逐字相同、末尾不完整，
独立视觉账本只发送过一次该请求。历史回读已经取到了完整的已保存字符串，
所以不能解释为回读分页藏起了后半段。
Opus 5 将该题归为视觉解释错误；更细的链路证据要求先考虑**生成完整性与结果复用**。

冻结视觉 provider 上限为 700 输出 token；只要文本非空就构造 completed，
没有持久记录/检查 finish_reason 和 usage。
“不完整文本被当完成并复用”有存档支持；
“恰好由长度上限截断”仍是推断，原始 finish_reason 没有保存。

建议明确显示缓存命中、请求预算、完成原因与输出是否完整。
内容不足时，模型可以改变聚焦问题或请求补全；重复读取缓存应显示其来自同一次观察。

### 5.3 观察不是自动可靠的证据

183:0 同一页的视觉观察出现正反冲突；40:0 不同页的“未见”被错误解释为相互矛盾。
17:8 存在表格行关联错误，190:2 属于图像内容辨识错误，
117:0 则把逐页视觉概述用于精确频次判断。
这些是不同故障，不能都用提高视觉重试次数解决。

其中某些视觉结果实际提供了关键可用信息，因此不能反推视觉工具应退役。
验证器需要看到观察的页范围和不确定性，不能将任何单条视觉否定当成全文事实权威。

### 5.4 调用与成本边界

原始 125 题首跑的独立视觉账本有 258 个发送记录：239 completed、14 failed（限流）、5 uncertain（连接）。
这份原始审计中的 177 次视觉工具调用与账本发送记录并非一一对应；透明重试还可能带来额外 HTTP 尝试。
主模型 trajectory token 汇总没有覆盖这部分独立视觉成本。

原诊断还存在将视觉 429 引导为调整画质/区域的问题；画质调整不能解决限流。
建议在 trajectory 中关联工具、页面和 provider 调用，记录错误类别、缓存、
finish_reason、usage 与退避，以区分请求失败、状态不明和仍在重试。

## 6. 笔记与上下文：不是“台账没写”

共同 123 题中，首跑 122 题有笔记，共 838 条，来自每步保存的公开 note。
原始运行的笔记长度审计未发现触及 4,096 字符上限的记录。
没有显式 findings 写/改工具调用或 source_refs，符合这次固定笔记路径，
不能继续用更早设计的“没写 source_refs 所以不压缩”解释本批。

笔记中附带的工具 ID 表示当时输入见过该结果，不证明笔记每个判断都受证据支持。
错误摘要也能持续入上下文；224:2 的文件页数误解就是例子。
轨迹能证明错误观察被重复保留，不能直接证明模型内部注意力机制或“智力不足”。

840 个 Attempt 输入中，53 个在首步之后没有 prior_tool_results，主要来自无工具的候选提交/修复步骤。
主模型固定只看紧邻前一步结果，而 reviewer 可看显式引用及近期成功结果；
正文没有永久丢失，但修复任务要额外回读。条目省略只在两题最后一步出现，
不足以把整批问题归为笔记大规模截断。

建议改善回读与来源引用，使修复输入携带导致拒绝的真实结果和页范围。
笔记应允许明确纠正旧判断，再评估保存与修改方式。

预算方面，840 个 input_pressure 均为 normal；冻结 L1 使用 900,000/1,350,000 字节阈值，
主模型实际输入峰值 101,742 token。本批没有终局 context-budget 超限证据，
不能把此潜在设计缺口归为八题失败的既定根因。
应衔接已有 token budgeting 和输出预留，区分窗口、输出上限与账户 TPM。

原始运行的上下文字节统计中，工具目录占成功 attempt 的 user JSON 字节约 73.27%，
findings 5.94%，旧工具正文 17.53%。这是字节比例，不是 token/费用占比，
也不证明可以无损删说明；精简或动态工具选择需另测能力变化。

## 7. Gate 的改进方向与对照实验

Opus 5 建议先把语义审查降为建议或关闭，以免其他工具修复被误拦抵消；
Astra 建议先修引用/回读和证据完整性，再比较 Gate。两者都认可实际误拦存在，
但目前证据不能决定哪个整体策略最好。

已有 always/off/conditional；conditional 在文档任务有工具结果时往往仍触发，
不能把它叫作 advisory。关闭语义审查也不等于取消权限、来源身份、schema 或持久状态检查。

建议固定模型、题集和预算，先回放固定候选/证据检查误拦，再做 always/off 配对。
回归集同时包含误拦题、曾得到真实纠正的题，以及一次通过的正负样本，不能只挑两道误拦题。
若增加 advisory，要明确它是否允许额外修订；多一次思考不是纯开关效应。

分别记录核心正确率、附加事实错误、未完成答复、证据真实性、延迟与 token。
Opus 5 曾估计部分错误可以挽回，这一改进幅度尚待对照实验验证。

## 8. 传输、配额与交付后处理

### 8.1 三道传输失败不是没有重试

203:1、206:0、207:2 的终局逻辑模型请求已耗尽六次物理尝试；
207:2 更早发生的错误曾恢复，208:1 也在传输失败后最终成功。
格式修复与传输尝试共享每逻辑调用预算，不是整轮只允许六次调用。

原持久记录没有保留每次具体 HTTP 状态/异常类型。
provider 内部有分类不等于 trajectory 完整保存了它，不能确认三题分别由 429、5xx、
连接重置还是账户限额造成。

三题本地 quota 累计等待约 57.525、52.582、226.876 秒；
失败且 usage 不明时的保守预留会放大排队，但预留不是实际计费。
129:0 quota 只等约 0.047 秒，是工具撞上整轮边界/完成未确认，不应合并为同类网络故障。
没有证据据此认定周额度耗尽。

建议在调用记录中补充错误类别、HTTP status、Retry-After、尝试序号、退避/排队和剩余 deadline，
据此调整重试次数与等待。

### 8.3 旧缺口与当时已经补的修复必须分开

冻结 runner 保存答案后不等待 post_commit，短命进程可能截断 daemon；
旧 scheduler 只尽力跑一页 job，也不能持续发现未来重试。
这是源码支持的生命周期缺口，不代表每个 pending 都在完全相同语句停止。

Astra 当时已记录开发工作区增加持续 worker、逐项 claim、重启发现/释放、
runner 有界等待，并分列 execution_ok/post_commit_complete/chain_complete。
另有独立的一题真实 API 冒烟全部通过；它不属于这 125+8 的成绩，不能混入分数。

这些修复记录反映当时工作区的状态。
后续验证仍需覆盖已写效果未结算、租约、窗口释放、崩溃恢复、MPS 长时间运行，
以及宿主停止时的任务交接。

## 9. 检索确实执行，但收益没有被证明

按共同 123 题统计，首跑 121/123（98.37%）检索状态 ready。另两题分别为未 prepare 直接读取即可完成，
以及入口传输失败尚未进入工具执行；不能直接宣称发生两次入库故障。

文档 source 的 321 个查询执行单元均记录三路与 reranker used；
picture source 三路各 58 次、reranker 52 次，合计三路各 379、重排 373。
六个 picture 查询没有对应 reranker 记录的原因未核定，不能说所有 source 全部重排。
这批记录未重现早先“宣称 Hybrid 实际只有 BM25”的静默降级。

112 个 matched 检索结果均标 partial，其中 102 个命中 context-pack 数量上限。
有界候选打包本来会省略内容；既不能把它一概当基础设施失败，
也不能假设省略的候选对题目完全无关。

索引 ready、方法 used、相关证据召回、进入上下文、模型正确使用，是五种不同指标。
需要把每路候选/排序、融合重排顺序、选入内容与截断原因关联到已核实的证据定位，
才能评价 Dense/Sparse/RRF/reranker 的价值。
本批不能证明换回 BM25 更好，也不能证明 Hybrid 必然优于它。

## 10. 后续改进方向
